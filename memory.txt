  项目概述

  Prompt Optimizer 是一个 AI 提示词优化工具，帮助用户编写更好的提示词来提升 AI
  输出质量。支持四种使用方式：Web 应用、桌面应用、Chrome 插件、Docker 部署。

  ┌──────────┬──────────────────────────────────────┐

  │ 前端框架 │ Vue 3 + TypeScript (Composition API) │
  ├──────────┼──────────────────────────────────────┤
  │ 构建工具 │ Vite + pnpm workspaces               │
  ├──────────┼──────────────────────────────────────┤
  │ 样式     │ TailwindCSS + PostCSS                │
  ├──────────┼──────────────────────────────────────┤
  │ 测试     │ Vitest + Playwright                  │
  ├──────────┼──────────────────────────────────────┤
  │ 桌面端   │ Electron (带自动更新)                │
  ├──────────┼──────────────────────────────────────┤
  │ 国际化   │ Vue-i18n                             │
  ├──────────┼──────────────────────────────────────┤
  │ 状态管理 │ 响应式 Composables (无 Pinia/Vuex)   │
  ├──────────┼──────────────────────────────────────┤
  │ UI 组件  │ Naive UI (优先使用)                  │
  └──────────┴──────────────────────────────────────┘

  ---
  架构概览

  Monorepo 结构

  packages/core (核心业务逻辑)
          ↓
  packages/ui (Vue 组件)
          ↓
  packages/web | extension | desktop (应用层)

  核心服务 (packages/core/src/services/)

  - llm/ - LLM API 集成 (OpenAI、Gemini、DeepSeek 等)
  - model/ - 模型配置管理，支持高级参数
  - prompt/ - 提示词优化和测试
  - template/ - 模板管理 (CSP 安全处理)
  - history/ - 优化历史记录
  - storage/ - 多适配器存储 (localStorage、IndexedDB、文件系统)
  - preference/ - 用户偏好设置

  Electron 架构

  桌面端采用 代理模式：
  - 主进程运行所有核心服务
  - 渲染进程通过 *-electron-proxy.ts 文件调用
  - IPC 序列化处理复杂对象传递
  - 业务逻辑保持在共享的核心服务中

  ---
  部署方式

  1. Web - Vercel 部署 (纯前端，无跨域限制问题)
  2. Desktop - Electron 应用 (无跨域限制，可连接本地模型)
  3. Chrome Extension - 浏览器插件
  4. Docker - 包含 MCP 服务器 (/mcp 路径)

      142 +### Vite 核心概念                                             
      143 +                                                              
      144 +#### 1. 开发服务器 (dev server)                               
      145 +                                                              
      146 +Vite 启动一个本地开发服务器，提供以下功能：                   
      147 +                                                              
      148 +| 功能 | 说明 |                                               
      149 +|------|------|                                               
      150 +| **模块热更新 (HMR)** | 修改代码后无需刷新页面即可更新 |     
      151 +| **ES 模块原生支持** | 浏览器直接支持 ES 模块导入 |          
      152 +| **按需编译** | 只编译当前访问的页面，不用构建整个项目 |     
      153 +| **Source Maps** | 调试时可以追踪到原始源码位置 |            
      154 +                                                              
      155 +#### 2. 环境变量                                              
      156 +                                                              
      157 +Vite 使用 `VITE_` 前缀定义环境变量：                          
      158 +                                                              
      159 +```typescript                                                 
      160 +// 在代码中使用                                               
      161 +console.log(import.meta.env.VITE_OPENAI_API_KEY)              
      162 +                                                              
      163 +// .env.local 文件示例                                        
      164 +VITE_OPENAI_API_KEY=your_key_here                             
      165 +```                                                           
      166 +                                                              
      167 +在本项目中：                                                  
      168 +- `envDir: monorepoRoot` 让 Vite 从 monorepo 根目录读取 `.env.
          +local`                                                        
      169 +- 这样可以共享同一套环境变量给所有子包                        
      170 +                                                              
      171 +#### 3. 依赖预构建 (optimizeDeps)                             
      172 +                                                              
      173 +首次启动时，Vite 会预构建依赖：                               
      174 +                                                              
      175 +```typescript                                                 
      176 +optimizeDeps: {                                               
      177 +  include: ['element-plus'],  // 预构建 Element Plus          
      178 +}                                                             
      179 +```                                                           
      180 +                                                              
      181 +预构建的好处：                                                
      182 +- 将 CommonJS 转换为 ESM                                      
      183 +- 合并小模块减少请求数                                        
      184 +- 缓存结果，下次启动更快                                      
      185 +

⏺ pnpm 的向上查找机制

  不是软链接，而是 pnpm 的虚拟化结构

  pnpm 的"向上查找"不是通过软链接实现的，而是通过它独特的 虚拟化 node_modules 
  结构。

  传统 npm 的结构（扁平化）

  node_modules/
      ├── vite/
      ├── vue/
      └── ...（所有依赖平铺在一起）

  pnpm 的结构（虚拟化）

  node_modules/
      ├── .pnpm/                    # 实际存储位置（store）
      │   ├── vite@7.2.7/
      │   │   └── node_modules/vite/
      │   │       └── bin/vite.js
      │   └── vue@3.x.x/
      │       └── node_modules/vue/
      │
      └── .bin/
          └── vite → 软链接 →
  ../../.pnpm/vite@7.2.7/node_modules/vite/bin/vite.js

  pnpm 向上查找的真正原理

  当你执行 pnpm vite 时：

  packages/web/node_modules/.bin/vite
      │
      ▼ 软链接
  packages/web/node_modules/.pnpm/vite@7.2.7/node_modules/vite/bin/vite.js
      │
      ▼
  /Users/pcm/Library/pnpm/store/v3/.../files/vite.js

  关键点：
  - .bin 目录中的命令是软链接
  - 软链接指向 .pnpm/ 目录中的实际文件
  - .pnpm/ 目录中的文件又是硬链接指向 pnpm store

  向上查找的真相

  实际上 pnpm 不需要"向上查找"，因为：

  1. 每个包的 node_modules/.bin/ 都已经通过软链接指向正确位置
  2. 每个包的 node_modules 可以直接 import 'vite' 因为已经正确链接

  packages/web/node_modules/
      └── vite → ../../.pnpm/vite@7.2.7/node_modules/vite

  所以当你执行 pnpm vite 时：
  - pnpm 在当前包的 .bin/ 中找到 vite
  - 软链接已经指向正确位置
  - 不需要向上查找

  如果当前包没有安装 vite

  如果 packages/web/node_modules/.bin/ 里没有 vite，pnpm 会：
  1. 查找根目录 node_modules/.bin/
  2. 或者报错 "command not found"

  这是 pnpm 的设计，不是传统意义上的"向上查找软链接"。

  ├────────────┼────────────────────────┼────────────────────────────┤

⏺ 简化理解

  简单比喻

  硬链接 = 同一个文件的不同名字
  比如：你给"张三"创建了一个文件叫"张三.txt"

  比如：桌面上有一个"电影.exe"的快捷方式
  如果原文件被删除，快捷方式就失效了

  ---
  为什么不能都用软链接？

  问题案例：

  如果全部用软链接：
  ~/.pnpm/vite@7.2.7/bin/vite.js  ← 原文件

  packages/web/node_modules/.bin/vite → 软链接 → ~/.pnpm/vite@7.2.7/bin/vite.js
  packages/ui/node_modules/.bin/vite → 软链接 → ~/.pnpm/vite@7.2.7/bin/vite.js

  - 原文件 ~/.pnpm/vite@7.2.7/bin/vite.js 被删除
  - 所有指向它的软链接都失效了
  - 其他项目再用 vite 就找不到

  用硬链接后：
  ~/.pnpm/vite@7.2.7/bin/vite.js  ← 真实文件（唯一一份）

  packages/web/node_modules/.pnpm/vite@7.2.7/.../vite.js ← 硬链接（另一个名字）
  packages/ui/node_modules/.pnpm/vite@7.2.7/.../vite.js ← 硬链接（另一个名字）

  - 删除 ~/.pnpm 中的原文件？不行，因为还有其他硬链接在使用
  - 只有当所有硬链接都被删除时，文件才会真正消失

  ---
  那软链接用在哪？

  软链接用在 .bin/ 目录：
  packages/web/node_modules/.bin/vite → 软链接 → .pnpm/.../vite.js

  这是为了方便调用，相当于"快捷方式"。

⏺ 理解文件系统的底层原理

  关键概念：inode

  在文件系统中，每个文件都有一个 inode（索引节点），它是文件的"身份证号"。

  磁盘数据区：
  ┌─────────────────────────────────────────┐
  │ inode: 123456    文件内容 "Hello"       │ ← 真实数据
  └─────────────────────────────────────────┘

  目录区：
  ┌─────────────────────────────────────────┐
  │ 文件名 "张三.txt" → inode 123456        │ ← 链接1
  │ 文件名 "李四.txt" → inode 123456        │ ← 链接2
  └─────────────────────────────────────────┘

  硬链接的原理

  当你创建硬链接时：
  # 原始文件
  echo "Hello" > 张三.txt

  # 创建硬链接
  ln 张三.txt 李四.txt

  实际情况：
  目录区：
  ┌─────────────────────────────────────────┐
  │ "张三.txt" → inode 123456 (链接数: 2)  │
  │ "李四.txt" → inode 123456 (链接数: 2)  │
  └─────────────────────────────────────────┘
        ↑                    ↑
        │                    │
        └──── 同一份数据 ────┘

  删除时发生了什么？

  rm 张三.txt

  删除"张三.txt"后：
  ┌─────────────────────────────────────────┐
  │ "李四.txt" → inode 123456 (链接数: 1)  │ ← 仍然存在
  └─────────────────────────────────────────┘

  删除操作实际上只做了：把"张三.txt"这个链接从目录中移除，并没有删除 inode 
  和数据。

  只有当链接数为 0 时，系统才会真正删除数据。

  ---
  软链接的情况

  # 软链接
  ln -s 张三.txt 王五.txt

  软链接完全不同：
  ┌─────────────────────────────────────────┐
  │ "张三.txt" → inode 123456               │
  │ "王五.txt" → inode 999999 → "张三.txt" │ ← 只是个"快捷方式"
  └─────────────────────────────────────────┘

  如果删除原文件：
  rm 张三.txt

  "张三.txt" 没了：
  ┌─────────────────────────────────────────┐
  │ "王五.txt" → inode 999999 → "张三.txt" │ ← 指向不存在的东西！
  └─────────────────────────────────────────┘
  软链接失效了！

  ---
  一句话解释

  ┌────────┬──────────────────────────────────────────┐
  │  类型  │               删除原文件后               │
  ├────────┼──────────────────────────────────────────┤
  │ 硬链接 │ 另一个文件仍可用（因为共享同一个 inode） │
  ├────────┼──────────────────────────────────────────┤
  │ 软链接 │ 失效（因为只是指向文件名的快捷方式）     │
  └────────┴──────────────────────────────────────────┘

❯ 软链接和硬链接的概念是操作系统层面的吗? 

⏺ 是的，这是操作系统层面的概念

  文件系统层级

  应用程序（如 pnpm、npm）
      ↓
  操作系统（提供系统调用）
      ↓
  文件系统（如 ext4、APFS、NTFS）
      ↓
  磁盘存储

  软链接和硬链接是文件系统提供的 原生功能，不是某个工具发明的。

  ---
  在哪里使用？

  你可以在命令行中直接使用：

  # 硬链接
  ln 源文件 目标文件

  # 软链接
  ln -s 源文件 目标文件

  这些是 Linux/macOS 自带的命令，任何程序都可以使用。

  ---
  验证方法

  # 创建测试文件
  echo "hello" > test.txt

  # 创建硬链接
  ln test.txt test_hard.txt

  # 创建软链接
  ln -s test.txt test_soft.txt

  # 查看
  ls -li

  输出：
  1234567 -rw-r--r-- 2 pcm staff 6 Feb 25 10:00 test.txt
  1234567 -rw-r--r-- 1 pcm staff 6 Feb 25 10:00 test_hard.txt   ← 同一 inode
  1234568 lrwxr-xr-x 1 pcm staff 8 Feb 25 10:00 test_soft.txt → test.txt

  - 2 和 1 是链接数
  - l 开头表示软链接
  - → 表示指向

  ---
  pnpm 只是"利用"了这个特性

  pnpm 并没有发明链接，它只是 利用 文件系统的原生功能来实现：

  - 节省磁盘空间
  - 保证依赖安全

  - 如果脚本同目录有 node，用本地的
  - 否则用系统全局的 node
  - 执行 vite.js，并传递所有参数 $@

  为什么要用 #!/bin/sh？

  #!/bin/sh 是脚本的shebang，告诉系统用哪个解释器来执行这个脚本。

  - #!/bin/bash → 用 bash 解释器

  else
    echo "不存在"
  fi  ← if 的结束标记

  ┌────────────┬─────────┬──────────────┐

  ├────────────┼─────────┼──────────────┤

  ├────────────┼─────────┼──────────────┤
  │ Python     │ if:     │ 自动根据缩进 │
  ├────────────┼─────────┼──────────────┤
  │ Java/C++   │ {       │ }            │
  ├────────────┼─────────┼──────────────┤
  │ JavaScript │ {       │ }            │
  └────────────┴─────────┴──────────────┘

⏺ NODE_PATH 的作用

  NODE_PATH 是 Node.js 的内置环境变量

  这不是 pnpm 自定义的，而是 Node.js 原生支持的。

  它的作用和 PATH 类似，但是用于 npm 模块查找：

  ┌───────────┬────────────────────────────────────────┐
  │   变量    │                  作用                  │
  ├───────────┼────────────────────────────────────────┤
  │ PATH      │ 查找可执行文件（命令）                 │
  ├───────────┼────────────────────────────────────────┤
  │ NODE_PATH │ 查找 npm 模块（import/require 的模块） │
  └───────────┴────────────────────────────────────────┘

  ---
  举例说明

  当你写代码 import vite from 'vite' 时：

  Node.js 查找 vite 模块的顺序：

  1. 当前目录的 node_modules/
  2. 父目录的 node_modules/
  3. ...
  4. NODE_PATH 指定的路径
  5. 全局安装的 node_modules/

  ---
  pnpm 设置的 NODE_PATH

  NODE_PATH=/Users/pcm/.../vite@7.2.7_.../vite/bin/node_modules:
            /Users/pcm/.../vite@7.2.7_.../vite/node_modules:
            /Users/pcm/.../vite@7.2.7_.../node_modules:
            /Users/pcm/.../node_modules/.pnpm/node_modules
             ↑
             多个路径用冒号分隔

  这告诉 Node.js：去这些位置找模块。

  ---
  为什么需要这么长？

  因为 pnpm 的依赖是隔离存储的：

  传统 npm 结构：
  node_modules/
      vite/
          node_modules/
              jiti/
                  ...

  pnpm 结构：
  .pnpm/
      vite@7.2.7_.../
          node_modules/
              vite/
                  bin/vite.js
                  node_modules/
                      jiti/
                          ...

  如果不用 NODE_PATH，Node.js 找不到 vite 内部的 jiti、yaml 等依赖。

  ---
  验证方法

  # 查看当前的 NODE_PATH
  echo $NODE_PATH

  # 临时添加自定义路径
  export NODE_PATH=/my/custom/path:$NODE_PATH

  # 在 Node.js 中查看
  node -e "console.log(process.env.NODE_PATH)"

⏺ Vite 不一定需要 index.html 在根目录

  默认行为

  Vite 默认会查找项目根目录的 index.html，但这是可以配置的。

  配置方式

  在 vite.config.ts 中可以指定入口文件：

  export default defineConfig({
    build: {
      rollupOptions: {
        input: {
          main: resolve(__dirname, 'index.html'),      // 主入口
          nested: resolve(__dirname, 'nested.html'),   // 其他入口
        }
      }
    }
  })

  本项目的配置

  // packages/web/vite.config.ts
  build: {
    rollupOptions: {

      }
    }
  }

  关键点

  ┌────────────────┬──────────────────────┐
  │      情况      │       是否需要       │
  ├────────────────┼──────────────────────┤
  │ 单页应用 (SPA) │ 通常需要 index.html  │
  ├────────────────┼──────────────────────┤
  │ 多页应用       │ 可以有多个 HTML 入口 │
  ├────────────────┼──────────────────────┤

  └────────────────┴──────────────────────┘
